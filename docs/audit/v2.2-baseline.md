## 缺陷根因定位（代码级）

1. **V22-A**：`build_findings` 只统计 `with_evidence` 用于 `B-EVIDENCE-STRIPPED`（仅当
   `with_evidence == 0` 全删时 FAIL）；`validate` 对"整题无任何证据字段"仅计
   `legacy_count` 出 WARN；`gate_decision(strict)` 仅拦 severity=FAIL，而
   `C-SEM-001`（evidence_status 缺失）severity 是 NOT_VERIFIED 不阻断。三个缺口
   叠加 → 混合题库在 strict 下放行。
2. **V22-B**：`validate()` 有顶层/逐题 isinstance 防护，但 `build_findings` L664/L667
   与 `locate_evidence` L574 直接 `.get`，命令入口无统一 Schema 前置校验。
3. **V22-C**：`locate_evidence` 仅使用 source_id/segment_id/source_quote；
   source_ref 是纯展示字段，前端/MD 直接原样渲染，无 canonical 引用交叉核对。
4. **V22-D**：`_locate_quote` 的 exact 分支是纯子串匹配，无最短证据/唯一性/
   语义支撑度维度。
5. **V22-E**：`gate_decision` 在 `build_findings` 计算 overall 之后才追加
   manifest FAIL，且报告只有单一 `overall` + `gate.blocked`，缺
   validation_status / release_status / check_execution_status 三维契约；
   `cmd_verify` 无 manifest 分支 return 0。

## 影响范围

- 正式交付可信度（V22-A/C/D 可让证据缺失、伪造、空洞的题库打着"已验证"旗号发布）
- 工程健壮性（V22-B 两个未处理异常路径）
- 机器可读契约（V22-E 报告字段不足以让外部调用者可靠判断发布状态与检查执行情况）
